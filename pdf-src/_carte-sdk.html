Avant de commencer

Ce document s'adresse à quelqu'un qui sait programmer en Python et qui veut ajouter quelque chose à PhytoScope : une analyse, une représentation, une sonification, un format d'export, une source de mesure. Il ne suppose aucune connaissance du code du logiciel — c'est même tout l'objet de l'interface décrite ici.

Ce que vous n'aurez pas à faire

Lire le moteur. Comprendre comment l'acquisition est ordonnancée. Savoir ce qu'est un EngineState. Un module reçoit une surface étroite et documentée, et c'est délibérément tout ce qu'il reçoit.

Ce que nous promettons

L'interface porte un numéro de version, en numérotation sémantique. Tant que le chiffre majeur ne change pas, un module écrit aujourd'hui fonctionnera : nous pouvons ajouter, nous ne pouvons pas retirer. Si le jour vient où il faut rompre cette promesse, le numéro majeur changera, le logiciel refusera de charger les modules anciens en le disant clairement, et ce document expliquera la migration.

Nous promettons aussi que votre module ne fera jamais tomber le logiciel. Une faute, où qu'elle survienne, désactive votre module et l'inscrit au journal ; la séance continue. C'est autant pour vous que pour l'utilisateur : on écrit plus librement quand on sait qu'une étourderie ne coûtera pas huit heures de mesure à quelqu'un.

Ce que nous ne promettons pas

Ce n'est pas un bac à sable. Votre module s'exécute dans le même processus, avec les mêmes droits que le logiciel : il peut écrire où il veut et lire ce qu'il veut. Nous n'avons ni les moyens ni l'intention de l'en empêcher — Python ne s'y prête pas, et un bac à sable mal fait donne une confiance qu'il ne mérite pas.

Ce que nous faisons à la place est plus honnête : nous disons clairement ce qu'un module doit faire, nous rendons ce chemin facile, et nous isolons les fautes. Un module qui écrit ailleurs que chez lui n'est pas bloqué ; il est mal élevé, et cela se saura.

1. Un premier module, en dix minutes

Commençons par le faire, on expliquera ensuite. À la fin de ce chapitre, trois lignes de votre cru s'afficheront dans l'onglet Multimètre du logiciel.

Créer le squelette

Le SDK est livré avec le code source, dans le dossier sdk/. Il contient un outil qui crée un module complet :

python3 src/sdk/outils/new_module.py mon-premier-module

Trois fichiers apparaissent :

FichierCe qu'il contient
module.pyle squelette, avec une capacité d'analyse qui fonctionne déjà
test_mon_premier_module.pydes essais qui passent, et qu'on étend
README.mdcomment l'installer, et ce qui reste à faire

L'intérêt de cet outil n'est pas de taper moins. C'est que le squelette produit est déjà correct : le manifeste est valide, les essais passent, et les pièges décrits plus loin sont déjà évités. On part d'un module qui marche, et l'on remplace ce qu'on veut.

L'éprouver, sans rien lancer

python3 -m pytest mon-premier-module/ -v

Cinq essais passent. Remarquez ce qu'ils n'exigent pas : ni le logiciel lancé, ni une carte branchée, ni une plante sur le bureau. Les essais fabriquent un signal plausible et un faux contexte, puis appellent votre code. C'est ce qui permet de développer un module dans le train.

Le faux contexte

Il est fourni avec les essais, et vous le recopierez. Il implémente ce dont votre module se sert, et rien d'autre. Si un essai échoue parce qu'une méthode y manque, c'est le signe que vous employez une partie de l'interface qu'il faudra aussi éprouver — ce qui est une bonne nouvelle, pas un ennui.

L'installer

# Linux
cp -r mon-premier-module ~/.config/phytoscope/modules/

# macOS
cp -r mon-premier-module ~/Library/Application\ Support/PhytoScope/modules/

# Windows
xcopy /E mon-premier-module %APPDATA%\PhytoScope\modules\mon-premier-module\

Relancez PhytoScope. Votre module apparaît à deux endroits : dans l'onglet Multimètre → Grandeurs scientifiques, où ses valeurs s'affichent parmi celles des modules livrés ; et dans l'onglet Diagnostic → Modules, qui liste ce qui est chargé.

Si rien n'apparaît

Allez au Diagnostic. La page Modules dit en une phrase ce qui s'est passé. C'est la page qu'on regarde en premier, avant de douter de soi :

Ce qui s'afficheCe que cela signifie
incompatible — vise l'API 2.0 votre manifeste annonce une version d'interface que ce logiciel ne connaît pas. Corrigez api=.
incompatible — bibliothèque absente vous avez déclaré exige=("scipy",) et scipy n'est pas installé. La commande à taper est donnée.
en_faute — TypeError au chargement votre code a levé. La trace complète est dans le journal (Ctrl+L).
desactive l'utilisateur l'a désactivé dans les réglages.
absent de la liste le dossier n'est pas au bon endroit, ou il ne contient pas de fichier module.py.

2. Anatomie d'un module

Un module est un dossier contenant un fichier module.py, qui déclare une classe héritant de Module. Tout le reste est facultatif.

Le manifeste, seul élément obligatoire

from phytoscope.api import Capacite, Manifeste, Module

class MonModule(Module):
    MANIFESTE = Manifeste(
        nom="mon-module",           # a-z, 0-9, tirets — l'identifiant
        titre="Mon module",         # ce que l'utilisateur lit
        version="1.0.0",
        api="1.0",                  # la version d'interface visée
        description="Ce que fait ce module.",
        auteur="Votre nom",
        licence="MIT",
        capacites=(Capacite.ANALYSEUR,),
    )

Le manifeste est lu sans exécuter votre code

Le logiciel analyse syntaxiquement module.py pour en extraire le manifeste, avant de l'importer. C'est ce qui lui permet de lister les modules présents, d'en désactiver un et de refuser celui qui vise une interface inconnue — sans avoir à exécuter du code pour savoir s'il faut l'exécuter.

Conséquence pratique : écrivez des valeurs littérales. Une valeur calculée — version=lire_version() — ne sera pas lue, et le défaut s'appliquera. Seules les constantes de Capacite font exception, parce qu'elles appartiennent au contrat.

Le cycle de vie

  1. __init__(contexte) — vous recevez le contexte. Ne faites rien de long ici : c'est appelé au démarrage, pour tous les modules, l'un après l'autre.
  2. installer() — une fois, après le chargement de tous les modules. C'est ici qu'on s'abonne et qu'on prépare ses fichiers.
  3. vos capacités sont appelées pendant la séance, à la demande.
  4. arreter() — une fois, à la fermeture. Fermez ce que vous avez ouvert ; les abonnements sont retirés pour vous.

Vos réglages

def reglages_par_defaut(self):
    return {"seuil_uv": 8.0, "montrer_le_detail": True}

# plus tard, dans une capacité :
seuil = contexte.reglages.get("seuil_uv", 8.0)

Le logiciel les conserve sous le nom de votre module et vous les rend au démarrage suivant. N'écrivez jamais vous-même dans le fichier de réglages du logiciel : il ne vous appartient pas, et sa forme peut changer.

3. Les cinq capacités

Une capacité est ce que votre module sait faire. Vous en déclarez une, plusieurs, ou aucune — un module qui ne fait quelque chose qu'à l'installation et à l'arrêt est parfaitement légitime.

Analyseur — calculer des grandeurs

Appelé par l'onglet Multimètre, toutes les deux secondes, et seulement quand la page est visible. Vous recevez une fenêtre de signal et rendez des nombres.

class MonAnalyse(Module, Analyseur):
    FENETRE_S = 60.0        # combien de secondes vous voulez
    SIGNAL_BRUT = True      # avant réjecteur et passe-bas

    def analyser(self, x, fs, contexte):
        return [Grandeur(
            cle="mon-indicateur",
            libelle="Mon indicateur",
            valeur=float(np.std(x)),
            texte=f"{np.std(x) * 1e6:.2f} µV",
            sens="Ce que ce nombre dit, et ce qu'il ne dit pas.",
        )]

Brut ou traité : le choix compte

SIGNAL_BRUT = True donne le signal avant le réjecteur de réseau et le passe-bas. C'est ce qu'il faut pour toute mesure de bruit : filtrer avant de mesurer le bruit revient à mesurer son propre filtre. Le réjecteur effacerait le résidu de secteur qu'on cherche justement à voir, et le passe-bas à 40 Hz effacerait la bande où se lit le bruit thermique.

False donne le signal traité, celui qu'on voit à l'écran. C'est ce qu'il faut pour analyser l'activité plutôt que la chaîne de mesure.

Descripteur — produire une courbe

Appelé à la demande de l'utilisateur, dans l'onglet Descripteurs. Ce n'est pas un chemin critique : un calcul d'une seconde est acceptable.

def decrire(self, x, fs, contexte):
    t = np.arange(x.size) / fs
    return [Trace(
        x=t, y=x * 1e6,
        titre="Ma représentation",
        x_libelle="temps (s)", y_libelle="µV",
        avertissement="Ce que cette représentation suppose.",
    )]

Sonificateur — faire des notes

Appelé pour chaque événement détecté. Soyez rapide : vous êtes dans la boucle de rendu musical. Rendre une liste vide signifie « pas de note pour cette valeur », ce qui est une réponse légitime.

def sonifier(self, valeur_v, contexte):
    gamme = (0, 2, 4, 5, 7, 9, 11)          # diatonique
    rang = int(abs(valeur_v) * 1e6) % len(gamme)
    return [NoteProposee(hauteur_midi=60 + gamme[rang],
                         velocite=70, duree_s=0.4,
                         origine_v=valeur_v)]

Le champ origine_v n'est pas décoratif : il conserve la valeur mesurée qui a produit la note. Une sonification dont on ne peut plus remonter à la mesure n'est plus une mesure.

Exportateur — un autre format

FORMAT = "Mon format"        # ce qui s'affiche dans la liste
EXTENSION = ".xyz"

def exporter(self, seance, cible, contexte):
    # `seance` est le dossier de la séance — LISEZ-Y, n'y écrivez pas.
    # `cible` est le fichier à produire — c'est le seul endroit où écrire.
    return True

Source — un flux de mesure

La plus délicate : elle s'exécute sur le chemin des données. Le logiciel vous isole autant qu'il peut, mais il ne peut pas vous isoler du temps que vous prenez. Une source lente fait tomber des échantillons, et cela ne se rattrape pas.

LIBELLE = "Ma carte"

def ouvrir(self, contexte): ...   # rend vrai si c'est ouvert
def lire(self): ...               # un bloc en volts, ou None
def fermer(self): ...

4. Les événements

Un module n'interroge pas le logiciel en boucle : il dit ce qui l'intéresse, et l'hôte l'appelle. C'est le seul moyen d'avoir des modules qui ne coûtent rien quand il ne se passe rien.

from phytoscope.api import EVENEMENT_DETECTE

def installer(self):
    self.contexte.abonner(EVENEMENT_DETECTE, self._sur_evenement)

def _sur_evenement(self, instant_s, amplitude_v):
    self._compte += 1

Ce que l'hôte garantit

Les rappels viennent du fil de l'interface

Jamais du fil d'acquisition. Un module qui met trente millisecondes à répondre ralentit l'affichage ; il ne fait pas tomber un échantillon.

Ce n'est pas une permission d'être lent. Trente millisecondes à chaque événement, sur une plante active, se voient à l'écran.

Un rappel qui lève est désabonné sur-le-champ, et l'incident inscrit au journal avec le nom du module. C'est délibéré : laisser branché un abonné fautif reviendrait à inscrire la même trace toutes les secondes, et à rendre illisible le journal — celui-là même dont on a besoin pour comprendre la panne.

Si votre module « cesse de réagir » après quelques minutes, regardez le journal : vous y trouverez la faute, et l'heure à laquelle il a été débranché.

S'abonner à ce qui n'existe pas encore

Ce n'est pas une erreur : le rappel ne sera simplement jamais appelé. C'est voulu. Une version ultérieure peut publier de nouveaux événements sans que les modules anciens aient à changer, et un module peut profiter d'un événement récent tout en restant chargeable sur une version plus ancienne.

5. Les pièges

Ce qui coûte une soirée quand on l'ignore. Ils sont tous réels : chacun a été rencontré en écrivant les modules livrés avec le logiciel.

Le manifeste doit être littéral

# NON — ne sera pas lu, le défaut s'appliquera
MANIFESTE = Manifeste(nom="mon-module", version=lire_ma_version())

# NON — pareil, même avec une constante du module
VERSION = "1.0.0"
MANIFESTE = Manifeste(nom="mon-module", version=VERSION)

# OUI
MANIFESTE = Manifeste(nom="mon-module", version="1.0.0")

Le logiciel analyse syntaxiquement votre fichier pour en extraire le manifeste, avant de l'importer. Exécuter un module pour savoir s'il faut l'exécuter serait absurde.

Ne jamais lever pour dire « rien à signaler »

# NON — désactive votre module pour toute la séance
if x.size == 0:
    raise ValueError("pas de signal")

# OUI
if x.size == 0:
    return []

Les libellés avec un nombre sont des gabarits

# NON — cette phrase ne peut entrer dans aucun catalogue de traduction
Grandeur(libelle=f"Écart d'Allan à {tau} s", ...)

# OUI
Grandeur(libelle="Écart d'Allan à {tau} s", params={"tau": f"{tau:g}"}, ...)

L'interface traduit d'abord, remplit ensuite. Un libellé où le nombre est déjà incrusté restera en français dans les dix autres langues.

Le champ « texte » ne porte que des unités

texte="+37.2 dB"                        # OUI — les symboles sont internationaux
texte="+37.2 dB au-dessus du plancher"  # NON — restera en français partout

Ce piège est d'autant plus facile qu'il ne se voit pas depuis une interface française.

Ne pas filtrer avant de mesurer le bruit

Le signal traité a traversé le réjecteur de réseau et le passe-bas à 40 Hz. Mesurer le bruit dessus revient à mesurer son propre filtre. Employez SIGNAL_BRUT = True.

N'écrire que chez soi

chemin = os.path.join(self.contexte.dossier(), "mon-fichier.txt")

Rien ne vous en empêche techniquement. Mais un module qui salit le dossier des séances sera désinstallé, et à juste titre.

N'importer que depuis phytoscope.api

# NON — cassera sans préavis, et nous ne le saurons même pas
from phytoscope.core.engine import Engine

# OUI
from phytoscope.api import Analyseur, Grandeur, Manifeste, Module

Le moteur change à chaque version. phytoscope.api ne change pas tant que le majeur ne change pas. Si quelque chose vous manque dans l'interface, dites-le : c'est ainsi qu'elle s'enrichira.

6. Pour aller plus loin

Lire les modules livrés

Ils passent par la même interface que les vôtres — aucun privilège, aucun raccourci. C'est ce qui garantit que cette interface suffit réellement, et cela a une conséquence agréable : pour savoir comment écrire un module, il suffit d'en lire un.

ModuleCe qu'il montre
grandeurs-scientifiques un analyseur qui calcule beaucoup, et explique chaque nombre
descripteurs-avances six représentations, avec leurs avertissements
empreinte-montage un module qui conserve un état sur le disque
export-csv le plus court exemple complet — soixante lignes

Ils vivent dans src/phytoscope/phytoscope/modules/.

Le SDK

Dans sdk/, avec le code source :

  • docs/ — cette documentation, en sept parties, au format Markdown ;
  • bonjour-monde/ — un exemple complet avec ses essais ;
  • outils/new_module.py — crée un module qui fonctionne déjà.

Si quelque chose vous manque

Dites-le. L'interface a été écrite en essayant d'anticiper, et l'anticipation se trompe toujours un peu. Une capacité qui manque, un événement qu'on n'a pas prévu, une donnée qu'on ne vous donne pas : ce sont les demandes qui font avancer une interface, et elles sont plus utiles que les compliments.

En revanche, nous ne l'enrichirons pas au coup par coup. Une capacité ajoutée est une capacité à tenir dix ans ; nous préférons attendre qu'une même demande revienne de trois côtés plutôt que de l'ajouter la première fois, et d'avoir à la porter ensuite.

Ce que nous ne ferons pas

Un bac à sable. Python ne s'y prête pas, et un bac à sable mal fait donne une confiance qu'il ne mérite pas. Nous préférons dire clairement ce qu'un module doit faire, rendre ce chemin facile, et isoler les fautes.

Un rechargement à chaud. Recharger un module dont des objets sont déjà référencés ailleurs laisse deux versions en mémoire et produit des bogues qu'on ne sait pas lire. Un redémarrage coûte trois secondes.
