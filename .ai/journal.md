# Intervention log

One entry per notable intervention, the most recent at the **bottom** — this
file is read the way a story is read, from the start. Every entry says **what
was done**, **why**, and **what remains to be checked**.

Format: `## YYYY-MM-DD — title`, then, as needed, `**Agent:**`, `**Done:**`,
`**Why:**`, `**Verified:**`, `**Careful:**`.

Entries before 2026-09-22 are still in French: the repository was written in
French until that date. They are being translated as the surrounding work
allows; the record of what happened is not rewritten, only its language.

**no fix applied** — it was an analysis, not a piece of work.

The worst of them (`P-1`) was checked by hand and confirmed: the software looks
for the board at `0x2E8A:0x10F5` (`protocol.py:38`, `usbdiag.py:38`,
`config.py:255`) while the firmware declares `0x1209:0x7A01`
(`usb_descriptors.c:40-41`). **It is the software that is wrong**: `0x1209` is
the free pid.codes range, made for open projects, whereas `0x2E8A` belongs to
Raspberry Pi and does not entitle us to assign a PID inside it. On Linux and
macOS a fallback on product name saves the discovery; on Windows `pyserial`
does not fill in `product`, and the control link is therefore unusable.

The good news, recorded too: `config_dir()`, `data_dir()`,
`shutil.disk_usage`, the systematic `encoding=`, `os.path.join` everywhere and
the Linux-only guards are exemplary. There is no rework to do.

### And then: the version contract, made readable from both sides

Asked for in the same session: a module must be able to read the host's API
version, and the host must be able to read the minimum the module expects.

`Manifest.api` had **always** been a minimum — that is what `compatible()`
computed — but nothing said so, nothing handed it back parsed, and the
refusal only named the two strings. Now:

| new | who asks | what it answers |
|---|---|---|
| `context.api_version` | the module | the version this host offers |
| `context.api_required` | the module | the minimum its own manifest declared |
| `context.api_at_least(v)` | the module | host at `v` or later, same major? |
| `manifest.api_required` | the host | the minimum, as `(major, minor)` |
| `manifest.api_satisfied_by` | the host | "API 3.0 or any later 3.x" |
| `registry.api_requirements()` | the host | every module's minimum at once |
| `parse_version(v)` | both | `"3.1.4"` → `(3, 1)`; unreadable → `(-1, -1)` |

One parser, exported, so that neither side writes its own regular expression —
two would disagree about `"3.1.4"` or `" 3.0 "` sooner or later. The patch
number is deliberately dropped: a patch clarifies behaviour, never shape, so
it cannot gate loading, and admitting it would invite modules to require one.

The point of `api_at_least()` is to make "aim for the lowest that will do"
actually possible. A module that needs 3.0 to work but would merely *like* a
field added in 3.2 should declare 3.0 and ask at run time; declaring 3.2
refuses it on every 3.0 and 3.1 host to gain one optional field.

The refusal now reads as an instruction:

```
needs at least API 2.0, but this software offers 3.0 — it wants API 2.0 or any later 2.x
```
